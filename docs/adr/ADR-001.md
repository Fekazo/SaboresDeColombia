# ADR-001: Selección de Stack y Arquitectura

**Fecha:** 2026-05-20  
**Autores:** Omar Felipe Rincon Fonseca, Johan Steven Carreño Daza  
**Estado:** Aceptado  

---

## Contexto

El proyecto "Sabores de Colombia" es una aplicación móvil universitaria para el descubrimiento de gastronomía colombiana. Se requiere una solución que:

1. Funcione en dispositivos Android con SDK ≥ 26 (95% del mercado colombiano).
2. Consuma APIs externas (TheMealDB, Google Translate).
3. Almacene datos localmente (recetas cacheadas, favoritos, traducciones).
4. Ofrezca una experiencia de usuario fluida con navegación entre múltiples pantallas.
5. Sea mantenible y evaluable académicamente bajo criterios de arquitectura de software.
6. Tenga un tiempo de desarrollo ≤ 5 horas para el MVP funcional.

---

## Alternativas Consideradas

### Alternativa 1: Flutter + Dart

| Criterio | Evaluación |
|---|---|
| **Lenguaje** | Dart — fuera del plan de estudios universitario |
| **Rendimiento** | Bueno (compilación nativa) |
| **Curva de aprendizaje** | Alta para el equipo (sin experiencia previa) |
| **Ecosistema** | Amplio pero menos maduro que Android nativo |
| **APIs nativas** | Requiere puentes (platform channels) |
| **Tiempo estimado** | 8-10 horas |
| **Riesgo** | Alto — equipo sin experiencia en Dart/Flutter |

**Conclusión:** Descartado por curva de aprendizaje y desviación del plan de estudios.

---

### Alternativa 2: Kotlin Multiplatform (KMM) + Compose Multiplatform

| Criterio | Evaluación |
|---|---|
| **Lenguaje** | Kotlin — dentro del plan de estudios |
| **Multiplataforma** | Android + iOS con código compartido |
| **Madurez** | En crecimiento pero con limitaciones en iOS |
| **Curva de aprendizaje** | Media-alta (configuración KMM compleja) |
| **Room en KMM** | Requiere configuración adicional |
| **Tiempo estimado** | 10-12 horas |
| **Riesgo** | Medio — bugs de tooling en fase beta |

**Conclusión:** Descartado por complejidad de configuración y riesgo de bugs. Excede el tiempo disponible.

---

### Alternativa 3: Android Nativo con Kotlin + Jetpack Compose (Seleccionada)

| Criterio | Evaluación |
|---|---|
| **Lenguaje** | Kotlin — primer lenguaje del programa académico |
| **UI** | Jetpack Compose — declarativo, moderno, Material 3 |
| **Arquitectura** | Clean Architecture + MVVM (estándar Google) |
| **DI** | Hilt — primera opción recomendada por Google |
| **Persistencia** | Room — nativo de Android Jetpack |
| **Red** | Retrofit + OkHttp — estándar de industria |
| **Navegación** | Navigation Compose — integrado con Compose |
| **Testing** | JUnit + Espresso + Compose Testing |
| **CI/CD** | GitHub Actions — gratuito para repositorios públicos |
| **Tiempo estimado** | 4-5 horas |
| **Riesgo** | Bajo — stack maduro y documentado |

**Conclusión:** Seleccionado por alineación con el plan de estudios, madurez del ecosistema, soporte oficial de Google y cumplimiento del tiempo límite.

---

## Decisión

Se adopta **Android Nativo con Kotlin** como plataforma, **Jetpack Compose** como framework de UI, **Clean Architecture + MVVM** como patrón arquitectónico, y **Hilt** como sistema de inyección de dependencias.

### Stack completo:

| Capa | Tecnología |
|---|---|
| Lenguaje | Kotlin 2.1.21 |
| UI | Jetpack Compose + Material 3 |
| Arquitectura | Clean Architecture (4 capas) + MVVM |
| DI | Hilt |
| Persistencia | Room 2.7.1 |
| Red | Retrofit 2.11.0 + OkHttp 4.12.0 |
| Navegación | Navigation Compose 2.8.9 |
| Imágenes | Coil 2.7.0 |
| Estado | StateFlow + Coroutines |
| Build | Gradle 9.3.1 + AGP 9.1.1 + Version Catalog |
| CI/CD | GitHub Actions |

## Consecuencias Positivas

1. **Alineación académica:** El stack coincide con lo enseñado en el programa de Ingeniería de Sistemas (Kotlin, Android, arquitecturas).
2. **Soporte oficial:** Todas las bibliotecas son parte de Android Jetpack o recomendadas por Google.
3. **Productividad:** Compose redujo el boilerplate de UI en ~60% comparado con XML Views.
4. **Mantenibilidad:** Clean Architecture permite cambiar fuentes de datos (API, Room) sin afectar la UI.
5. **Testing:** La separación de capas facilita tests unitarios de ViewModels y Repositorios.
6. **Version Catalog:** Centraliza todas las versiones de dependencias en un solo archivo (`libs.versions.toml`), facilitando actualizaciones.
7. **CI/CD integrado:** GitHub Actions permite build automático en cada push sin configuración adicional.

## Consecuencias Negativas

1. **Solo Android:** No hay soporte para iOS. Si se requiere en el futuro, requeriría reescribir la UI (posible migración a KMM).
2. **Tamaño de APK:** ~8-10 MB por inclusión de bibliotecas Jetpack (aceptable para el contexto).
3. **Curva de Hilt inicial:** La configuración de Hilt + KSP tomó ~45 minutos extra por incompatibilidades de versiones (Kotlin 2.1.21, AGP 9.1.1, KSP 2.3.8).
4. **Google Translate no oficial:** El endpoint gratuito podría ser descontinuado sin previo aviso. Mitigación: la app sigue funcionando sin traducción (muestra texto original).
5. **Room sin migración:** Se usa `fallbackToDestructiveMigration()` lo que implica pérdida de datos en cambios de esquema (aceptable para MVP).
